# 🎁 コラボレーション応募・抽選システム（Collab Project）

## 1. プロジェクト概要

- **開発期間**：2026.09 ～ 2026.09
- **開発人数**：1名（個人開発）

### プロジェクトについて

アニメ・コラボレーションイベントの応募を想定したWebアプリケーションです。

応募者情報を登録し、同一電話番号による重複応募を防止する機能を実装しました。

また、管理者向けページから応募者情報を確認し、当選者を抽選できる機能も実装しています。

## 3. 主な機能

### 応募機能
- 応募者情報の登録
- 応募時の入力値バリデーション
- 電話番号を基準とした重複応募チェック

### 例外処理
- 同一電話番号による重複応募を検出
- `IllegalArgumentException` を利用した不正な応募処理の制御
- `@Column(unique = true)` を設定し、DBレベルでも重複登録を防止

### 入力値検証（Validation）
- 名前・電話番号・メールアドレスなどの入力値を検証
- `@Valid` を利用して不正な入力を検出
- 入力内容に応じたエラーメッセージを表示

### 同時リクエストに対するテスト
- 同一電話番号による複数の応募リクエストを想定したテストを実施
- 同一電話番号が重複して登録されないことを確認

### 管理者ページ・抽選機能
- 登録された応募者情報を管理者ページから確認
- 応募者一覧を表示
- 登録された応募者の中から当選者を抽選する機能を実装

## 4. アーキテクチャとデータフロー

### Layered Architecture（レイヤードアーキテクチャ）

`Controller` → `Service` → `Repository` → `Database`

各層の責務を分離し、保守性を意識した構成にしています。

- **Controller**
  - HTTPリクエストを受け取り、応募処理や画面遷移を担当

- **Service**
  - 応募処理や重複チェックなどのビジネスロジックを担当

- **Repository**
  - 応募者データの検索・保存を担当

- **Entity**
  - 応募者情報とDBテーブルのマッピングを担当

## 5. トラブルシューティング・学んだこと

### 重複応募の判定方法

当初は、応募時に重複しているかどうかをBoolean値で判定する方法を検討しました。

しかし、複数の応募処理が発生する状況を考慮し、電話番号を重複応募の判定基準として設定しました。

その上で、

1. Service層で電話番号の重複をチェック
2. 重複している場合は例外を発生
3. DB側にも`UNIQUE`制約を設定

という形で、アプリケーション側とデータベース側の両方から重複登録を防止する構成にしました。

この実装を通じて、単純に条件分岐で処理するだけではなく、**アプリケーション側のチェックとDB側の制約を組み合わせてデータの整合性を守ること**について学びました。

---

### レイヤードアーキテクチャについて

個人開発を通じて、Controller・Service・Repositoryの役割を分離することで、それぞれの責務を明確にできることを学びました。

特に、Controllerに処理を集中させるのではなく、ビジネスロジックをService層に分離することで、コードの見通しや保守性を高められることを理解しました。
